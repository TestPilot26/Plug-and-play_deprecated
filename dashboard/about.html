The thinking behind Engagement OS

Why this system is shaped the way it is — because the reasoning matters as much as the functionality.

The problem it solves

Every client engagement built with Devin generates hard-won know-how: which approaches worked, what clients always ask for late, how long things really take. Normally that knowledge lives in one engineer's head and evaporates. The next engagement starts from a blank prompt and relearns the same lessons — at full price.

Engagement OS turns each engagement into structured data, mines that data for repeatable patterns, and hands the next engagement a ready-made starter kit. Every project makes the following one cheaper. That compounding is the whole point.

The loop

Capture → Learn → Suggest
Each engagement logs what was used and how it went (Capture). A weekly automated session finds repeated patterns and drafts suggestions (Learn). New problem statements get matched against that history to produce a ranked, evidence-backed starter kit (Suggest).

Crucially, capture records not only which playbooks were used, but what was built from scratch — the ad-hoc functionality and procedures with no playbook behind them. When the same ad-hoc work shows up in two or three engagements, the system flags it as a playbook candidate, the same way Devin suggests knowledge notes. The library grows from observed behavior, not from someone remembering to write documentation.

The design principles (and why)

PrincipleReasoning
The system drafts; humans decide. Automated pattern-mining is confidently wrong sometimes. A wrong playbook suggestion silently applied could send a whole build down the wrong path. So every promotion — candidate to playbook, pattern to library — passes a human approval gate, and every suggestion shows the past engagements it's based on, so a bad match is spottable.
Boring technology on purpose. The whole system is a CSV file, markdown documents, and two small scripts with zero dependencies. A learning system that itself needs maintenance is a tax that kills learning systems. Nothing here can meaningfully break, and everything is inspectable by a non-programmer.
Minimal behavior change. Learning loops die when retros feel like homework. Humans do exactly three things: run triage at the start (~2 min), confirm a pre-filled retro at the end (~5 min), and review a weekly summary (~5 min). Everything else is automated.
Earn trust with data volume. With fewer than ~10–15 engagements, "patterns" are mostly noise. So the suggest layer stays advisory, states its sample sizes, and refuses to invent a pattern from a single example. Early on, it's organized memory; the recommender role is earned later.
Metrics are health indicators, not targets. If "reuse rate" became a target, engineers would force-fit templates onto novel problems (Goodhart's law: when a measure becomes a target, it stops measuring what you wanted). The dashboard informs; it doesn't grade people.
Honest accounting, including the risks. Impact is measured only on engagements where a suggestion was actually used, compared against a pre-playbook baseline — and the expected cost of wrong suggestions, stale playbooks, and maintenance is subtracted, not ignored. The retirement rule is written down up front: if the system doesn't pay for itself within a quarter of normal volume, simplify or stop.

What "good" looks like

Six months in, success looks like: new engagements start with a triage session that cites real precedents; two or three promoted playbooks cover the most common engagement shapes; quotes are made from measured effort ranges rather than gut feel; and this dashboard's reuse trend is rising without anyone being told to raise it.
